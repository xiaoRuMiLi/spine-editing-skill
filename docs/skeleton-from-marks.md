# 骨架生成流程（手标关节 → bones.json → 审阅图）

> 适用场景：一张平涂插画，**人在图上圈出关节**，工具读出圈的位置生成骨架，并把骨架
> 画回原图供人复核。
> 代码在 `src/spine_forge/rig/`，命令行入口 `spine-forge skeleton`。
> 关键原则：**关节位置以人的标记为准**，自动检测只负责"把标记变成数字"。

---

## 一、一条命令

```bash
spine-forge skeleton <原图> --out <目录> \
    --marks <带标记的图.png>  \
    --joints <关节表.json>     \
    --name girl
```

产物：

```
<目录>/
├── marks.json            # 读到的标记坐标（x, y，图像像素）
├── marks_numbered.png    # 标记编号图（复核"我读到的点对不对"）
├── joints.json           # 关节表（吸附后的最终值，可再次编辑）
├── bones.json            # 关节 + Spine 局部变换（x/y/rotation/length）
└── skeleton_panel.png    # ★ 交付图：骨架画在原图上 + 右侧坐标表
```

`--joints` 可以省略：此时只读标记并出 `marks.json` / `marks_numbered.png`，
用于"人标完 → 先确认读数"这一步。`--no-snap` 关闭吸附。

---

## 二、标记怎么画（人有且只有一个要求）

**画空心圈**（椭圆环，黑色，直径 15~25px，线宽 3~5px），圆心 = 关节位置。

为什么必须是空心：

| 画法 | 能否识别 | 原因 |
|---|---|---|
| 空心圈 | ✅ | 圈内有洞，洞的质心就是关节 |
| 实心点 | ❌ | 与瞳孔、眉毛、暗部无法区分 |
| 一条短线 | ❌ | 不围出洞 |
| 圈太大（>40px） | ❌ | 会被尺寸过滤 |

同一张图里可以混有黑线（描边、发丝）——它们不围洞，不会误判。

---

## 三、识别算法（`rig/markers.py`）

```
1. 暗色掩膜：三通道都 < 80 记为"墨"
2. 从 (0,0) 对背景做 flood fill
3. 没被 flood 到、又不是墨的亮区 = 洞
4. 洞的面积 12~900 px、边长 ≤40、填充率 ≥0.30 → 是一个标记
5. 质心 = 关节坐标；两个洞相距 ≤14px 视为同一圈被切开 → 合并
```

**为什么用"洞"而不是"暗色团块"**：第一版按暗色团块找，24 个结果里有 4 个是**眼睛和眉毛**
（实心暗），而头发里的圈反而漏了。洞检测天然排除所有实心暗块和线条。

**已知退化情况**（都会显式暴露，不会静默出错）：

| 情况 | 表现 | 处理 |
|---|---|---|
| 圈被发丝切成两半 | 两个相邻洞 | `merge_close_marks` 合并 |
| 圈画得太扁，洞是一条缝 | 检测不到 | 关节表里手填该点；`snap` 会报告"这一点离最近的标记 X px" |
| 圈压到深色区域 | 洞被墨吃掉 | 同上，手填 |

## 四、关节表（`joints.json`，可直接编辑）

```json
{"name": "girl", "joints": [
  {"name": "chest", "parent": "hips", "base": [397, 583], "tip": [460, 427]}
]}
```

- 坐标是**图像像素，y 向下**（和人在图上看到的完全一致，不用换算）。
- `base` = 骨头起点（旋转轴），`tip` = 骨头指向处；**长度 = 两点距离**。
- 父骨必须排在子骨之前；父骨不存在会直接报错（不猜）。

### 吸附（snap）

表里的点若在 12px 内有标记，会被拉到标记上，并在 `bones.json` 的 `snapped` 里
逐条记录"哪个点、移动了多少、落到哪"。这样"表"和"标记"不一致时永远看得见。

---

## 五、补骨规则（标记没覆盖到的部分）

照着 `mix-and-match` 示例的结构补，原则是**每条肢体 = 若干段 + 末端**：

| 补什么 | 依据 | 说明 |
|---|---|---|
| `root` | 示例 `root` | 全身原点，放在骨盆中心（零长度） |
| `hips` | 示例 `hips` | 骨盆；两腿挂在它下面，不从它的尖端分支 |
| `shoulder_*` 零长度控制骨 | 示例 `arm-front-control` | 耸肩/转肩只动它；零长度骨旋转必须为 0 |
| `neck` 单独一节 | 示例 `neck`（长 43.9） | 给头一个独立枢轴 |
| `hair` 挂在 `head` 下 | 示例头发同理 | 马尾跟头动 |
| 每肢 `a → b → 末端` | 示例 `arm-up → arm-down → hand` | 肘、膝可弯 |

## 六、坐标换算（`rig/skeleton.py`）

Spine 的骨是**局部**的：`x/y` 相对父骨、且处在父骨的旋转坐标系里。

```
世界坐标（图像） → 世界坐标（Spine，y 翻一次：y' = H - y）
父骨变换求逆 → 子骨的局部 x/y
局部 rotation = 世界朝向 − 父骨世界朝向
```

三件事必须记住：

1. **y 只翻一次**，就在这一层做；下游不要再翻。
2. **子骨起点常常不等于父骨尖端**：腿从骨盆侧面长出，臂从胸腔侧面长出。偏移必须**算**，
   不能假设 `x = 父骨长度`。
3. **零长度骨**（肩部控制骨）`atan2(0,0)` 没有意义，必须显式给 `rotation = 0`。

---

## 七、审阅图（`rig/overlay.py`）

`skleleton_panel.png` 的规矩：

- 原图 **1:1 贴**，不缩放——缩放会让"看起来在手臂上"变成假象；
- 骨头按链上色（蓝=躯干、紫=头颈、绿=头发、红=手臂、青=腿）；
- 右侧表格打印**和 bones.json 完全相同的数字**（坐标、长度），左边看到什么、右边就是什么。

---

## 八、验收口径

1. `pytest` 全绿（`tests/test_rig.py`，13 个用例）。
2. `marks_numbered.png` 上的编号点数量、位置 = 人手标的数量、位置。
3. `skeleton_panel.png` 上每根骨的起点**落在关节上**、线段**落在肢体内部**。
4. `bones.json` 里 `snapped` 为空，或每一条都是可解释的小位移（≤2px）。

本次（girl）：20 个标记 → 20 根骨，吸附只动了 2 个点（1.5px / 1.8px）。

---

## 九、已知限制

- 只认**空心圈**；其他标记约定要改 `markers.py` 的常量。
- 标记是"点"，不是"骨段"：**骨头的走向仍需要人给**（在 `joints.json` 里写 base/tip）。
  骨架走向 = 艺术判断，工具不猜。
- 图必须是浅色纸张背景；深色海报/照片背景会让 flood fill 失效。
- 一根骨一个关节：多段手指、多节马尾目前用"一根骨一个部件"近似。

## 十、IK 与跟随约束（按官方示例的字段生成）

`mix-and-match` 示例里只有三类约束：**IK**（脚）、**path**（手脚沿曲线）、**transform**（头发/裙摆/
帽子/瞳孔跟随）。我们的图没有 path 附件，所以生成前两类：

| 约束 | 名称 | 内容 | 依据示例 |
|---|---|---|---|
| IK ×4 | `foot_r` / `foot_l` / `hand_r` / `hand_l` | 目标骨 `ik_foot_*` / `ik_hand_*` 挂在 `root` 下；链条 `leg→shin`、`arm→fore`；`bendPositive:false` | `{"type":"ik","target":"foot-front-IK","bones":["leg-up","leg-down"],"bendPositive":false}` |
| transform ×2 | `head-follow` | `head-control` → `head`，`mixRotate:1, mixX:1, mixY:1` | 示例 `head-control` 驱动 `head-back-control` |
| | `hair-follow` | `head-control` → `hair`，`mixRotate:0.35, mixX:0.1, mixY:0.1`（滞后摆动） | 示例头发 `mixX:0.05~0.15` |

**为什么不做 path 约束**：path 约束需要一根 `path` 附件（沿手脚画的曲线），我们这套拆分没有这种美术。
以后要加 = 一个新附件 + 一条约束，不需要改架构。

### 编辑方法

`joints.json` 里直接改 `constraints`：

- 想让膝盖朝另一边弯 → `bendPositive: true`；
- 想让头发更"甩" → 把 `hair-follow.mixRotate` 调大（1 = 完全跟随，就不是滞后了）；
- 不想让手被 IK 拉 → 删掉对应一条即可，其余不受影响。

### 三个必须记住的点

1. **IK 目标骨必须零长度**。吸附阶段曾把目标的 tip 拉到另一个标记上，造出 1px 的长度，
   约束行为跟着变 —— 现在零长度骨的 tip 强制等于 base。
2. **链条必须是"父→子"顺序**（`leg_r, shin_r`）。顺序反了 IK 解不出来，但不会报错，
   只会姿势诡异，所以 `validate()` 会检查这两根骨在骨架里存在。
3. **目标骨挂在 `root`**。挂在胸腔上的话，身体一转，脚也会被带走 —— 示例同样把
   `foot-front-IK` 挂在 `skeleton-control` 下。

### 审阅图怎么读

橙色的**菱形**就是控制/目标骨（`head-control`、`ik_*`），虚线连着它驱动的关节。
普通关节是圆点。所以一眼能看出"这根脚骨由这个目标拉"。

### 十·补：接入部件之后才暴露的两个约束坑

1. **`bendPositive` 不能用固定值**。用 false 时左手臂整条翻到了头顶 —— 因为画的姿势本来就是
   另一侧弯。现在按**现有姿势**算：取两根骨方向在 Spine 空间（y 向上）的叉积，正负即弯曲方向。
   （girl：双腿 false，双臂 true。）
2. **不要给 transform 约束写 `properties` 范围块**。示例里用 `{"rotate":{"to":{"rotate":{"max":100}}}`
   是把源骨骼的角度映射进 0~100 这个窗口；头骨本身 89°，结果头被拧了约 60°。
   只用 `mixRotate/mixX/mixY` 才是「按比例混合」。需要限幅时再来加，并且必须按该骨的实际角度设范围。

两个坑的共同点：**运行时不报错**，只是姿势错了。所以「渲染一版看图」是唯一的验收手段。

### 十·补二：两种打包模式

| 模式 | 产物 | 用途 |
|---|---|---|
| `--mode atlas`（默认） | `girl.json` + `girl.atlas` + `girl.png` | 网页/游戏运行时（spine-player、Unity 等） |
| `--mode images` | `girl.json` + `images/*.png`（每件一张） | **Spine 编辑器**直接打开，不需要图集 |

两者附件数据完全一致，只是"图从哪来"不同。如果 Spine 报找不到纹理，先用 images 模式排除图集问题。
